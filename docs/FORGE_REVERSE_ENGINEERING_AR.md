# تقرير الهندسة العكسية لـ Forge — نسخة Claude في Macaly مقابل GitHub

**تاريخ الفحص:** 2026-10-16  
**مصدر نسخة Claude:** مشروع Macaly المسمّى `Forge Studio — GitHub Edition`، مع مراجعة مشروع `Forge Agent Gateway` المنفصل.  
**مستودع التطوير المعتمد:** `venom3-byte/Project1` على GitHub.  
**النطاق:** فحص الكود وعقود الواجهات وتدفقات التشغيل؛ لا تُعتبر أوصاف README أو أسماء الوحدات وحدها إثباتاً لاكتمال ميزة.

## 1. الخلاصة التنفيذية

نسخة Macaly ليست مجرد لوحة 3D. توجد فيها نواة محرك PlayCanvas، وفيزياء Rapier، وبروتوكول وكيل قائم على أوامر منظمة، وطبقات أصول/مواد/رندر/لعب/إعادة تشغيل وQA، وواجهة Live Vision منفصلة. كما يوجد مشروع Macaly آخر هو Forge Agent Gateway يضيف جسر HTTPS لإضافة Godot وواجهة هاتف وطابور أوامر ومراجعة لعمليات الكتابة.

قبل هذا النقل، كان فرع GitHub `main` يحتوي محرراً أصغر مبنياً على React وThree.js، وMCP لتعديل مشهد محدود إلى عناصر ثلاثية الأبعاد، ومشغّل Playwright للفحص البصري؛ لكنه **لم يكن يحتوي مجلد `public/forge/` الذي تستعمله نسخة Macaly كواجهة Forge الكاملة**. لذلك كانت النسختان متباعدتين في البنية والوظائف، ولا يصح افتراض أنهما تطابقان بعضهما لمجرد أن اسم Worker يحتوي Claude Game Editor.

هذا الفرع ينسخ نواة واجهة Forge الثابتة من مشروع Macaly إلى `public/forge/` مع إبقاء المحرر القديم متاحاً على الجذر أثناء التحقق. لا يُحذف أي مشروع Macaly ولا يُعدّل.

## 2. خريطة معمارية نسخة Macaly

### A. واجهة المحرر ونواة 3D

- `public/forge/index.html` هي واجهة المحرر ذات تقسيم المشهد/Hierarchy/Inspector وأدوات الأصول.
- `forge-engine.js` ينشئ تطبيق PlayCanvas من CDN، ويهيئ Rapier للفيزياء، والكاميرا والإضاءة والـGround، ويحتفظ بسجل كيانات ومواد وحالة تشغيل.
- `forge-runtime.js` و`forge-spatial.js` و`forge-gizmo.js` تنظم واجهات النواة والتحديد والتحويل والرؤية المكانية.
- `forge-ui.js` يربط اللوحة بالـengine، ويحمّل وحدات الميزات عند الحاجة، ويعرض تقارير التشخيص والحالة.
- `forge-project.js` و`forge-export.js` و`forge-production.js` تمثل طبقات حفظ المشروع واستيراد/تصدير الأصول وإجراءات تجهيزها. وجود الكود لا يعني أن جميع الصيغ أو حالات الحافة قد اجتازت اختبارات فعلية.

### B. أنظمة الإنتاج داخل المحرر

توجد وحدات مستقلة لـ2D، الرسوم والتحريك، الذكاء الاصطناعي/اللعب، بيانات اللعب، الشبكات، المؤثرات، الخامات/الشيدرات، التضاريس، التسجيل وإعادة التشغيل، والرندر وQA. هذه طريقة التوسع الصحيحة للمشروع: وحدات واضحة وعقد بيانات واختبارات، وليس ملف واجهة واحداً يحاول تنفيذ كل شيء.

### C. التحكم بالوكيل

- `forge-agent.js` يعرّف أوامر منظمة مثل التشخيص، الكيانات، الإنشاء والتحويل والتحديد والتشغيل.
- التصميم التاريخي يستخدم WebSocket عند المسار `/live` مع رسائل `forge-command` و`forge-result`.
- `FORGE_AGENT_PROTOCOL.md` يفضّل معرّفات ثابتة وأوامر deterministic على النقرات الإحداثية، ويطلب دورة inspect → execute → re-inspect → QA → proof → save/build.
- هذا الاتصال يحتاج خدمة خلفية متوافقة؛ وجود WebSocket client داخل الملفات الثابتة لا يثبت أن endpoint متاح في أي استضافة.

### D. Live Vision

ملفات `live-vision.js` و`vision.html` و`vision-control.mjs` و`vision-controller.mjs` توضح فصل الرؤية عن منطق المحرك. وثائق 3.7 تصف جلسة متصفح مستمرة، وإطارات حية، وإدخال ماوس/كيبورد/لمس، وقراءة حالة منظمة للمقارنة مع الصورة. الواجهة الثابتة تفحص `./api/vision/status` وتُعطّل زر الخادم عند غياب الجسر؛ وهذا سلوك صريح أفضل من إظهار اتصال وهمي.

### E. Asset pipeline

البحث المرفق يحدد glTF/GLB كعقد تبادل للـ3D، ويُميّز بين تصدير المصدر الأصلي وتصدير مشهد مشتق وmanifest. ملف `forge-pipeline.mjs` يضع أساساً لتجهيز GLB عبر glTF-Transform وMeshopt/LOD، لكنه يحتاج تبعيات وبيئة خادم وتشغيل اختبارات قبل اعتباره جزءاً عاملاً من نسخة GitHub. أصول 2D والـsprites والخامات والصوت والتحريك تحتاج نفس نمط المصدر → معالجة → تحقق → حزمة runtime.

### F. Godot Bridge المنفصل

مشروع `Forge Agent Gateway` في Macaly ليس هو واجهة PlayCanvas نفسها. إنه جسر HTTPS خروجياً من إضافة Godot مع اقتران مؤقت، صلاحية جلسة، قائمة أوامر مسموحة، حماية مسارات، وموافقة قبل الكتابة. هذه طبقة تكامل اختيارية لتشغيل محرك محلي، وليست دليلاً على أن Godot مثبت أو متاح في بيئة GitHub الحالية.

## 3. ما ثبت في نسخة GitHub عند بدء هذا النقل

- `mcp/worker.js` يوفّر MCP Streamable HTTP مع عمليات قراءة للمستودع، وحالة المشهد، والتحكم المحدود في عناصر المشهد، وأدوات متصفح مرئية.
- أدوات `visual_*` تتطلب `AGENT_API_KEY` للـWorker. هذا مفتاح تفويض لجسر المحرر، وليس مفتاح مزود LLM. لم تُقرأ قيم أسرار ولا تُطبع.
- `mcp/visual-agent-runner.mjs` يشغّل Chromium/Playwright فعلياً ويعيد ملاحظات DOM وصور شاشة وأخطاء runtime. تمت إضافة سحب ماوس حقيقي والتحقق منه على فرع منفصل ثم دمجه في GitHub.
- نموذج F-16 في `assets/F16C_Block50.obj` اجتاز فحصاً بنيوياً وأبعادياً؛ فحص الأبعاد لا يثبت وحده المطابقة البصرية.
- إصلاح اختيار ملف MTL الذي كان يُتجاهل دُمج في `main`، ونجح البناء المنشور واختبار بصري بعده.

## 4. الفجوات التي يجب سدها بالترتيب

1. **فصل الواجهات عن ادعاءات الميزات:** اختبار كل وحدة فعلية في المتصفح والتأكد من أن كل زر له handler، وكل handler يصل إلى runtime، وكل عملية ترجع حالة/خطأ يمكن التحقق منهما.
2. **توحيد بروتوكول الوكيل:** اختيار مصدر حالة واحد، IDs ثابتة، JSON schema لكل أمر، حدود payload، نتائج قابلة للتكرار، وموافقات على التغييرات عالية التأثير.
3. **جسر بصري يعمل فعلياً:** تسلسل لقطة/إجراء/لقطة، سحب وتكبير ولمس، استقرار الإطار، وتسجيل أدلة؛ لا تكتفِ بصور منفصلة غير مرتبطة بالفعل.
4. **استيراد الأصول:** تحقق من ملفات GLB/GLTF/OBJ وMTL والخامات والحجم والوحدات والمحاور والمواد والأوزان والأنيميشن. يجب أن يكون فشل التحميل مرئياً، لا fallback صامتاً.
5. **Image-to-3D:** جمع عدة صور/زوايا أو video، معايرة الكاميرا إن أمكن، بناء mesh أولي، إصلاح mesh/topology، UV/مواد، retopology وLOD، collision، ثم مقارنة render مع المرجع وقياس التشابه. لا يوجد اختصار عام يحوّل صورة واحدة إلى هندسة دقيقة من كل الجهات.
6. **جودة الرندر:** مسار متدرج WebGL2/WebGPU مع PBR وإضاءة وpost-processing، مع Native/Blender/Godot backend عند الحاجة إلى هندسة أو رندر لا يمكن للمتصفح إنجازه بكفاءة. لا ندّعي أن Forge يعادل Nanite/Lumen أو Blender Cycles/Eevee لمجرد استخدام نفس أسماء سير العمل.
7. **بناء ألعاب فعلية:** scene graph + asset registry + physics + animation + gameplay graph + audio + VFX + saves + profiling + export + automated regression. يُقبل كل نظام بعد اختبار صغير مستقل ثم تكامل.

## 5. معنى «التحكم بدون API»

لا يحتاج النموذج إلى مفتاح API خاص بمزود LLM إذا كان يتعامل مع Forge عبر Computer Use/المتصفح أو عبر MCP متوافق مع الجسر المصرّح. لكن التحكم بين عمليتين ما زال يحتاج قناة نقل (مثل MCP أو WebSocket أو HTTP) وهو ليس اتصالاً سحرياً بلا واجهة. الحل المراد هو **عدم ربط Forge بمزوّد واحد**: بروتوكول محايد + أدوات متصفح مرئية + حالة منظمة + تفويض محلي/قصير العمر، مع إبقاء الأسرار خارج الواجهة.

## 6. معايير قبول التطوير

- لا ميزة مكتملة بلا اختبار آلي ومسار runtime فعلي.
- عند استيراد أصل: إثبات الاسم والصيغة والأبعاد وحالة المادة واللقطة من المحرر.
- عند تنفيذ وكيل: حفظ الأمر ونتيجته والأخطاء وصورة قبل/بعد.
- عند تعديل المشروع: فرع صغير، اختبار، دليل مرئي، ثم دمج.
- يجب أن تكون رسائل الخطأ واضحة وأن تبقى الملفات والأسرار والإعدادات المحمية خارج صلاحيات الوكيل.
